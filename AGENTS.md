# AGENTS.md — OLHM (Open Linux Hardware Monitor)

Эти правила действуют только в репозитории OLHM и дополняют общие правила из `~/.codex/AGENTS.md`. Если задача не требует изменений, не вноси их «заодно».

## 1. Цель и границы проекта

OLHM — открытая утилита для Linux, предназначенная для обнаружения оборудования и мониторинга его основных показателей.

- До версии **1.0** разрабатываются только обнаружение железа, сбор и обработка показателей, их вывод в CLI и GUI.
- **1.0** — законченная графическая утилита, определяющая основные компоненты компьютера и показывающая доступные рабочие показатели.
- Стресс-тесты, бенчмарки, разгон, управление оборудованием, удалённый мониторинг и другие дополнительные функции **не реализовывать до 1.0**, если пользователь прямо не изменил план.
- Не расширяй задачу по собственной инициативе, даже если новая функция кажется полезной.

## 2. Дорожная карта — основной ориентир

Придерживайся принятой дорожной карты OLHM. Очередность версий:

- **0.1** — определение CPU в консоли.
- **0.2** — мониторинг CPU в консоли.
- **0.3** — стабилизация ядра и разделение на три слоя.
- **0.4** — первый GUI для CPU.
- **0.5** — оперативная память.
- **0.6** — накопители и файловые системы.
- **0.7** — видеокарты.
- **0.8** — материнская плата, датчики и сеть.
- **0.9** — объединение функций, тестирование и подготовка выпуска.
- **1.0** — стабильная графическая утилита мониторинга оборудования.

Перед работой определяй, к какой текущей версии и задаче относится изменение. Не перескакивай на следующий этап и не меняй состав версий без прямого согласования. Если пользователь дал конкретную задачу вне очереди, выполняй её, не перестраивая автоматически весь план.

## 3. README и документация

- **`README.md` обновляй только при подготовке или выпуске очередной запланированной версии: 0.1, 0.2, …, 0.9 и 1.0.**
- Не изменяй README после каждого коммита, исправления, рефакторинга или небольшой новой функции.
- Между релизными этапами README не трогай, кроме случая, когда пользователь прямо попросил изменить его.
- Не меняй номер версии, статус этапа и формулировки о готовности без фактического завершения соответствующей версии.
- В README описывай только реально реализованные и проверенные возможности; планы отделяй от готовых функций.
- Дорожную карту не переписывай при обычной разработке. Её изменение требует прямого запроса пользователя.
- Не создавай дополнительную документацию и отчёты без практической необходимости.

## 4. Три слоя архитектуры

Сохраняй чёткое разделение:

1. **Collection** — обнаружение устройств и чтение исходных данных Linux/драйверов.
2. **Processing** — расчёты, проверка, нормализация единиц и единая модель показателей.
3. **Presentation** — консольный и графический вывод готовых данных.

- GUI и CLI не должны напрямую читать `/proc`, `/sys` или обращаться к аппаратным API в обход Collection.
- Collection не должен зависеть от GUI, а Processing — от конкретного способа вывода.
- Новые виды оборудования подключай отдельными модулями, используя общие интерфейсы там, где это оправданно.
- Не вводи абстракции «на будущее», если они не нужны текущему этапу. Сохраняй простоту и возможность расширения.
- Консольный интерфейс должен продолжать работать после добавления GUI.

## 5. Совместимость с разным железом и Linux

Пиши максимально переносимый в пределах Linux код, а не решение только для компьютера разработчика.

- Не зашивай модель CPU/GPU, производителя, число ядер, пути конкретного устройства, имена датчиков или порядок устройств.
- Учитывай Intel, AMD и, где применимо, другие архитектуры CPU; интегрированные и дискретные GPU, несколько устройств и отсутствие отдельных категорий оборудования.
- Предпочитай стандартные и документированные интерфейсы Linux. Особенности производителей и драйверов изолируй в отдельных адаптерах.
- Не считай, что один и тот же набор датчиков доступен на всех системах и дистрибутивах.
- Не привязывайся без необходимости к одному дистрибутиву, окружению рабочего стола или способу установки.
- При отсутствии драйвера, датчика или доступа приложение должно продолжать работу и показывать понятный статус, а не падать.
- Базовый мониторинг по возможности должен работать без root. Не запрашивай повышенные права ради необязательного показателя.
- Не добавляй тяжёлые зависимости или внешние фоновые службы без обоснованной потребности.

## 6. Достоверность измерений

- **Никогда не выдумывай значения.** Нет данных — показывай «недоступно» или конкретную причину, а не `0`.
- Не приписывай датчик CPU, GPU или плате по догадке: сопоставление должно быть обосновано.
- Загрузку CPU и скорости I/O/сети рассчитывай по разнице измерений за известный интервал; учитывай первый опрос и сброс счётчиков.
- Приводи показатели к согласованным единицам и проверяй корректность расчётов.
- Не выдавай отсутствие поддержки датчика за неисправность оборудования.
- Различай статическую информацию об устройстве и динамические показатели; не опрашивай неизменные данные с частотой мониторинга.
- Сбор показателей не должен блокировать GUI или создавать заметную нагрузку на систему.

## 7. Порядок реализации и проверки

- Работай небольшими законченными изменениями в пределах текущей задачи.
- Сначала реализуй корректный сбор, затем обработку, затем вывод.
- При исправлении ошибки устраняй причину, а не маскируй неверное значение в интерфейсе.
- Не ломай работающий CLI и уже готовые модули ради нового устройства или GUI.
- Проверки выбирай по масштабу правок: сначала целевые тесты, полная сборка/тестирование — только когда это действительно необходимо или явно запрошено.
- Для аппаратно-зависимого функционала проверяй доступные сценарии и предусмотри отсутствие устройств/датчиков. **Не заявляй о тестировании на железе, к которому не было доступа.**
- Не устанавливай пакеты, не запускай приложение с повышенными правами, не публикуй релизы и не изменяй системную конфигурацию без прямого запроса.

## 8. Результат работы агента

Кратко укажи, что изменено, к какой версии дорожной карты это относится и какие проверки действительно выполнены. Если что-то нельзя было проверить, обозначь ограничение. Не объявляй этап или релиз завершённым, пока не выполнены его критерии готовности.
