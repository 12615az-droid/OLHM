# OLHM 0.4 — нерешённые проблемы

Дата актуализации: 25 октября 2026 года. Версия: `0.4.0`.

Проблемы 01 и 02, связанные с определением троттлинга, исправлены и удалены из
этого списка. Критическая температурная тревога теперь является отдельной
метрикой, а троттлинг учитывает рост числа событий и накопленного времени
`core/package_throttle_total_time_ms` за интервал.

Ниже перечислены только проблемы, которые ещё требуют решения. Нумерация сохранена
для связи с первоначальным отчётом. RAM, GPU и функции следующих версий дорожной
карты не считаются недостатками версии 0.4.

## Список проблем

| ID | Приоритет | Проблема |
| --- | --- | --- |
| 03 | P2 | Общий ответ «нет» возможен без базы сравнения для части счётчиков |
| 04 | P2 | GUI не подписывает текущую и критическую температуры |
| 05 | P2 | Ошибка первого чтения критического порога сохраняется на всю сессию |

## 03. Частично отсутствующая база сравнения маскируется общим ответом «нет»

**Место:** функция `throttling` в `src/processing/cpu_monitor.rs`.

Если предыдущего значения одного счётчика нет или оно прочитано с ошибкой,
обработка пропускает этот источник. Другой неизменный счётчик может сделать общий
результат равным «нет», хотя для пропущенного источника сравнение невозможно.

**Подтверждение:** первый замер CPU 0 равен 5, а чтение счётчика CPU 1 завершается
ошибкой. Следующий замер содержит CPU 0 = 5 и CPU 1 = 100. Результат — «нет», хотя
изменение CPU 1 за интервал определить нельзя. То же возможно при появлении нового
источника без предыдущего значения.

**Что исправить:** учитывать полноту сравнения всех обнаруженных источников.
Подтверждённый рост может давать «да», но неполная база не должна превращаться в
достоверный общий ответ «нет».

**Критерий проверки:** после восстановления счётчика сначала показывается ожидание
базы или неполнота данных; сравнение выполняется после двух успешных замеров.

## 04. В GUI текущая и критическая температуры не имеют подписей

**Место:** карточки температур в `src/presentation/gui.rs`, функция `metric_ui` и
форматирование в `src/presentation/format.rs`.

Карточка датчика вызывает `metric_ui` для каждой метрики, но функция выводит только
значение без `Metric.label`. Пользователь видит, например, `45.0 °C` и `100.0 °C`,
не понимая, где текущая, а где критическая температура. CLI уже выводит подписи.

**Что исправить:** показывать подписи «Температура» и «Критическая температура»
в карточках датчиков, включая недоступные значения.

**Критерий проверки:** GUI явно отображает обе подписи рядом с соответствующими
значениями.

## 05. Критический порог не восстанавливается после неудачного первого чтения

**Место:** создание и опрос температурных источников в
`src/collector/cpu/monitor.rs`.

Результат чтения `temp*_crit` сохраняется при создании сборщика и затем клонируется.
Если первое чтение завершилось ошибкой, эта ошибка остаётся на всю сессию. Наличие
`temp*_crit_alarm` также проверяется только один раз.

**Подтверждение:** при создании сборщика существует `temp1_input`, но отсутствует
`temp1_crit`. После появления файла со значением `100000` последующие замеры всё
равно содержат `NotAvailable`.

**Что исправить:** повторять неудачные чтения метаданных с ограничением частоты,
не превращая редкий статический опрос в опрос на каждом кадре. Аналогично учитывать
появление файла тревоги.

**Критерий проверки:** временно недоступный порог или интерфейс начинает
отображаться после восстановления без перезапуска приложения.

## 06. JSON-экспорт сообщает Broken pipe и завершается с ошибкой

**Место:** обработка ошибок и JSON-сериализация в `src/main.rs`.

Главная функция распознаёт `BrokenPipe` только в `std::io::Error`. Ошибка записи из
`serde_json::to_writer_pretty` возвращается как `serde_json::Error`, поэтому
досрочное закрытие принимающей стороны не обрабатывается штатно.

**Воспроизведение:**

```sh
bash -o pipefail -c 'target/debug/olhm collect cpu --format json | head -c 0'
```

Текущий результат — код возврата `1` и сообщение о `Broken pipe`.

**Что исправить:** распознавать закрытие pipe также внутри ошибки JSON, не скрывая
остальные ошибки записи.

**Критерий проверки:** раннее закрытие pipe завершает JSON-вывод без сообщения об
ошибке; другие ошибки вывода по-прежнему возвращаются пользователю.

## 07. Состав аппаратных источников фиксируется при запуске

**Место:** обнаружение источников в `src/collector/cpu/monitor.rs`.

Списки hwmon-каналов, powercap-зон и файлов счётчиков троттлинга создаются только
из первого снимка. Если драйвер загрузился или перезапустился после запуска OLHM,
существующая сессия не замечает новый источник и может продолжать читать старый
путь с ошибкой.

**Подтверждение:** сборщик создаётся без hwmon-устройства. Затем появляются
`hwmon5/name = coretemp` и `temp1_input = 40000`. Повторные замеры существующего
сборщика остаются без температур, хотя новый полный сбор видит устройство.

**Что исправить:** добавить редкое повторное обнаружение источников либо явное
обновление сессии. При замене устройства необходимо перепроверять его идентичность
и сбрасывать базы счётчиков.

**Критерий проверки:** загрузка или перезапуск датчика и появление powercap-зоны
обрабатываются без перезапуска OLHM и без смешивания старых и новых данных.

## Проверки и ограничения

- После исправления проблем 01 и 02 прошли 46 тестов: 42 библиотечных и 4 CLI.
- `cargo clippy --offline --features gui --all-targets -- -D warnings` прошёл без
  предупреждений.
- Проблемы 03, 05 и 07 подтверждены отдельными файловыми сценариями; проблема 06
  воспроизведена на локальном бинарнике; проблема 04 подтверждена по пути GUI-вывода.
- Физический перегрев CPU не создавался. Исправление троттлинга проверено
  искусственными снимками и файловыми фикстурами.
- Этот документ не доказывает отсутствие других ошибок и не объявляет этап 0.4
  завершённым.
