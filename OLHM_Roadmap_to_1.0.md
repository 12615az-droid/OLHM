# OLHM — Open Linux Hardware Monitor
## План разработки до версии 1.4

**Статус:** план проекта  
**Платформа:** Linux  
**Модель разработки:** сначала для личного использования, затем открытый проект для других пользователей  
**Граница плана:** стабильный выпуск OLHM 1.0 и последовательное развитие интерфейсов до OLHM 1.4.

---

## 1. Идея и цель

OLHM (Open Linux Hardware Monitor) — открытая утилита для Linux, которая определяет установленное оборудование и показывает его основные рабочие показатели в реальном времени.

Ориентир по направлению развития — OCCT, но **OLHM 1.0 не является аналогом OCCT по набору функций**. До 1.0 проект занимается исключительно обнаружением оборудования, чтением показателей и их понятным отображением.

Разработка начинается с **консольной утилиты для процессора**. После создания стабильного ядра появляется графический интерфейс. Остальные категории оборудования добавляются последовательно, без переписывания уже работающих компонентов.

### Что должно получиться к 1.0

- Полноценное настольное приложение с графическим интерфейсом.
- Автоматическое обнаружение основных компонентов ПК.
- Отображение их названий и доступных характеристик.
- Мониторинг основных доступных показателей в реальном времени.
- Стабильная работа без обязательных прав администратора.
- Понятное сообщение, когда конкретный датчик или показатель недоступен.

### Что сознательно исключено до 1.0

Стресс-тесты, бенчмарки, проверка стабильности, управление вентиляторами и разгоном, изменение параметров оборудования, уведомления, экспорт отчётов, постоянная запись истории и удалённый мониторинг. Их разработка **не должна задерживать 1.0**.

## 2. Архитектура: три независимых слоя

### Слой 1 — Collection / Сбор данных

Задача: обнаружить устройства и получить исходную информацию от Linux и доступных драйверов.

- CPU, RAM, GPU, накопители, материнская плата, сетевые интерфейсы.
- Статические характеристики: модель, производитель, объём, драйвер и т. п.
- Динамические показатели: загрузка, температура, частота, использование памяти и прочее.
- Отдельный сборщик для каждой категории устройств.
- Никаких расчётов для пользовательского интерфейса и никакой зависимости от GUI.

### Слой 2 — Processing / Обработка

Задача: превратить исходные данные в достоверные и единообразные показатели.

- Расчёт загрузки и скоростей по разнице между измерениями.
- Нормализация единиц: %, °C, Вт, МГц/ГГц, ГиБ, об/мин, МиБ/с.
- Привязка датчиков к правильным устройствам, когда это достоверно возможно.
- Проверка значений, защита от ошибок и обработки пропущенных измерений.
- Единая модель устройств и показателей для любых интерфейсов.
- Отдельные состояния: «доступно», «не поддерживается», «нет доступа», «ошибка чтения».

### Слой 3 — Presentation / Вывод

Задача: отобразить готовые данные, **не собирая их напрямую**.

- Сначала CLI: простой вывод информации и обновляемых показателей в терминале.
- Затем GUI: обзор системы и страницы отдельных категорий оборудования.
- CLI и GUI должны использовать один и тот же слой обработки.

**Правило архитектуры:** новый тип оборудования добавляется в Collection и Processing; интерфейс получает его через общую модель. Замена CLI на GUI не должна требовать переписывания логики мониторинга.

## 3. Дорожная карта по версиям

### OLHM 0.1 — Обнаружение CPU в консоли

**Цель:** первый минимальный, но законченный результат.

**Функции:**
- Определение производителя и модели CPU.
- Определение архитектуры.
- Количество логических процессоров; количество физических ядер — когда система позволяет определить достоверно.
- Вывод основных характеристик в терминал.
- Обработка ситуации, когда часть характеристик отсутствует.

**Готово, когда:** приложение запускается из терминала, распознаёт процессор и выводит корректные сведения без графического интерфейса.

### OLHM 0.2 — Живой мониторинг CPU в консоли

**Функции:**
- Общая загрузка CPU.
- Загрузка отдельных логических процессоров.
- Текущие частоты, если доступны через систему.
- Температура CPU, если доступен корректно идентифицированный датчик.
- Потребление CPU в ваттах при наличии поддерживаемого источника: текущее значение
  мощности или среднее за интервал, рассчитанное по разности счётчиков энергии.
  Отдельные CPU-пакеты показываются раздельно; их поддомены не суммируются повторно.
- Обновление показателей с заданным интервалом.

**Готово, когда:** значения обновляются без перезапуска утилиты; загрузка и мощность по счётчикам энергии рассчитываются по двум последовательным измерениям. Первый замер, сброс/переполнение счётчика и отсутствие доступа обрабатываются явно; отсутствующие данные не подменяются нулями, лимиты мощности и TDP не выдаются за текущее потребление.

### OLHM 0.3 — Стабилизация ядра и трёхслойная архитектура

**Функции:**
- Выделение отдельных слоёв Collection, Processing и Presentation.
- Единый формат описания устройства и показателя.
- Настраиваемый интервал опроса.
- Корректная обработка ошибок чтения и исчезновения датчиков.
- Снижение лишней нагрузки от самого мониторинга.
- Проверка работы CPU-модуля на нескольких конфигурациях.

**Готово, когда:** консольный CPU-монитор устойчиво работает, а добавление нового модуля не требует изменений внутренней логики CLI.

### OLHM 0.4 — Первый графический интерфейс (CPU)

**Функции:**
- Создание основного окна OLHM.
- Отображение модели CPU, загрузки, частот, температуры и потребления в ваттах при наличии данных.
- Общая загрузка и данные по логическим процессорам.
- Автоматическое обновление без зависания интерфейса.
- Отображение недоступных показателей.
- Сохранение работоспособности CLI.

**Готово, когда:** CPU можно полноценно отслеживать в графическом окне, использующем то же ядро, что и консольная версия.

### OLHM 0.5 — Оперативная память (RAM)

**Функции:**
- Определение доступного системе объёма RAM.
- Использовано / доступно / всего.
- Процент использования RAM.
- Общие показатели swap: всего / использовано, если применимо.
- Отображение показателей в CLI и GUI.

**Готово, когда:** раздел RAM показывает корректные значения, сопоставимые с системными инструментами Linux. Физические характеристики отдельных модулей ОЗУ не обязательны для 1.0, поскольку их чтение не всегда доступно без дополнительных прав.

### OLHM 0.6 — Накопители и файловые системы

**Функции:**
- Определение основных физических накопителей: SSD, HDD, NVMe, если они доступны системе.
- Модель и ёмкость, когда эти сведения предоставляются.
- Отображение подключённых файловых систем и их заполненности.
- Текущая активность чтения и записи, когда доступны подходящие счётчики.
- Раздельное отображение физических дисков, разделов и точек монтирования.

**Готово, когда:** пользователю понятно, какие диски установлены, сколько места занято и какие показатели активности доступны. SMART, ресурс SSD и температура накопителя не являются обязательными для 1.0.

### OLHM 0.7 — Видеокарты (GPU)

**Функции:**
- Обнаружение интегрированных и дискретных GPU.
- Название, производитель и используемый драйвер, насколько информация доступна.
- Загрузка GPU, температура, частоты и видеопамять — **только для поддерживаемых сочетаний GPU и драйвера**.
- Отображение нескольких видеокарт в одной системе.
- Отдельные адаптеры сбора показателей для AMD, Intel и NVIDIA по мере доступности интерфейсов.

**Готово, когда:** OLHM корректно обнаруживает GPU, отображает реально доступные показатели и честно указывает ограничения драйвера. Полнота телеметрии не обязана быть одинаковой для разных производителей.

### OLHM 0.8 — Материнская плата, датчики и сеть

**Функции:**
- Определение производителя и модели материнской платы, когда доступны DMI-данные.
- Отображение версии BIOS/UEFI, если доступна.
- Список обнаруженных аппаратных датчиков с осмысленными названиями, если их можно установить.
- Температуры и скорости вентиляторов при наличии поддерживаемых датчиков.
- Обнаружение сетевых интерфейсов и отображение текущей скорости приёма/передачи данных.
- Отсутствие дублирования датчиков, уже отнесённых к CPU или GPU.

**Готово, когда:** общий список оборудования охватывает основные компоненты ПК, а неподдерживаемые датчики не выдаются за неисправные.

### OLHM 0.8.5 — Информация о системе и окружении

**Функции:**
- Название дистрибутива Linux, его версия и архитектура системы, например `NixOS 26.11 (Zokor) x86_64`.
- Название и версия ядра, например `Linux 6.18.57`.
- Время работы системы с момента загрузки (uptime).
- Количество установленных пакетов с раздельным указанием источников, которые удалось достоверно определить, например `2074 (nix-system), 1476 (nix-user)`.
- Название и версия графического окружения, например `KDE Plasma 6.8.0`.
- Оконный менеджер или композитор и тип графической сессии, например `KWin (Wayland)`.
- Отображение системной информации в CLI и GUI через общую модель данных.
- Явное состояние «недоступно» для полей, которые система или окружение не предоставляют.

**Правила достоверности:**
- Не определять дистрибутив, окружение или менеджер пакетов по догадке; использовать подтверждённые системные файлы, интерфейсы и переменные текущей сессии.
- Не смешивать пакеты из разных областей установки: системные, пользовательские и другие поддерживаемые источники показывать раздельно.
- Не считать отсутствие графической сессии ошибкой: на сервере, в TTY, контейнере или SSH графическое окружение может быть недоступно.
- Не требовать root и не устанавливать дополнительные службы ради получения этих сведений.

**Минимальный вывод:**

```text
OS:       NixOS 26.11 (Zokor) x86_64
Kernel:   Linux 6.18.57
Uptime:   10 mins
Packages: 2074 (nix-system), 1476 (nix-user)
Desktop:  KDE Plasma 6.8.0
Session:  KWin (Wayland)
```

**Готово, когда:** CLI и GUI показывают доступные сведения об ОС, ядре, времени работы, пакетах и графической сессии на общей модели; отсутствие отдельных данных обрабатывается явно, а результат проверен как минимум в графической сессии и в окружении без GUI.

### OLHM 0.9 — Сборка единого приложения и тестирование

**Функции:**
- Главная страница с кратким состоянием системы.
- Разделы CPU, RAM, GPU, накопителей, материнской платы/датчиков, сети и информации о системе.
- Единый стиль отображения величин и состояний.
- Выбор интервала обновления из ограниченного набора значений.
- Проверка корректности и плавности обновления интерфейса.
- Тестирование на нескольких дистрибутивах и разных конфигурациях оборудования.
- Подготовка инструкции по установке и использованию.

**Готово, когда:** все основные разделы собраны в единое приложение, критические ошибки устранены, известные ограничения документированы.

### OLHM 1.0 — Первый полноценный стабильный выпуск

**Обязательный результат:**
- Завершённое графическое приложение для Linux.
- Автоматическое обнаружение основных категорий оборудования.
- Отображение моделей и ключевых характеристик, когда они доступны.
- Мониторинг основных показателей в реальном времени.
- Поддержка нескольких CPU/GPU/накопителей там, где это применимо; интерфейс не должен предполагать ровно одно устройство каждого типа.
- Работа при обычных правах пользователя для базовых сценариев.
- Корректная обработка недоступных датчиков и неподдерживаемых драйверов.
- Стабильная работа без зависаний, чрезмерной фоновой нагрузки и обязательных внешних служб OLHM.
- Документация, инструкция по запуску и хотя бы один проверенный способ установки.
- Сохранение консольного интерфейса как дополнительного способа просмотра данных.

**Критерий выпуска:** пользователь устанавливает OLHM, открывает графическое окно, видит найденное оборудование и его основные доступные показатели без ручной настройки для базового сценария.

### OLHM 1.1 — Локализация интерфейсов

**Цель:** сделать GUI и человекочитаемый вывод CLI доступными на нескольких языках без изменения ядра мониторинга.

**Функции:**
- Вынесение пользовательских надписей, сообщений об ошибках и состояний доступности в локализуемые ресурсы.
- Русская и английская локализации как обязательный первоначальный набор.
- Автоматический выбор языка по системной локали и возможность явно выбрать язык.
- Единая терминология для GUI и CLI: устройства, единицы измерения, состояния ошибок и недоступности.
- Безопасный fallback на основной язык при отсутствии или неполноте перевода.
- Аппаратные названия, модели, серийные номера и исходные сообщения драйверов не переводятся и не изменяются.

**Готово, когда:** GUI и обычный текстовый CLI полностью работают минимум на русском и английском языках, переключение языка не влияет на сбор данных, а отсутствующий перевод не приводит к пустым подписям или падению.

### OLHM 1.2 — Простой режим GUI

**Цель:** предоставить понятный режим без избыточной технической информации для пользователей, которым нужен быстрый обзор состояния компьютера.

**Функции:**
- Переключение между простым и подробным режимами GUI.
- В простом режиме показываются название устройства, основные показатели и понятные предупреждения.
- Служебные пути sysfs, идентификаторы, сырые значения, источники датчиков и расширенные технические поля скрываются из основного представления.
- Подробный режим сохраняет доступ ко всей подтверждённой информации, уже доступной в OLHM.
- Скрытие поля не должно менять сбор, расчёты или достоверность показателей.
- Недоступность важного показателя и критическое состояние остаются видимыми в обоих режимах.

**Готово, когда:** пользователь может переключить режим без перезапуска, простой режим не перегружен техническими деталями, а подробный режим не теряет существующие сведения.

### OLHM 1.3 — Настройка GUI через конфигурационный файл

**Цель:** сохранять внешний вид и поведение GUI без изменения исходного кода.

**Функции:**
- Конфигурационный файл в стандартном пользовательском каталоге по XDG Base Directory Specification.
- Настройка языка, простого/подробного режима, интервала обновления, видимости разделов и отдельных групп показателей.
- Сохранение основных параметров окна и выбранной страницы, если это надёжно поддерживается GUI-фреймворком.
- Документированный формат конфигурации с версией схемы и безопасными значениями по умолчанию.
- Проверка диапазонов и типов; неизвестные или повреждённые параметры не должны приводить к падению приложения.
- Настройки Presentation не меняют работу Collection и Processing и не могут включать запись или управление оборудованием.

**Готово, когда:** GUI применяет поддерживаемые настройки после запуска, корректно переживает отсутствующий, частично устаревший или повреждённый конфигурационный файл и позволяет вернуться к значениям по умолчанию.

### OLHM 1.4 — Настраиваемый вывод консольной версии

**Цель:** дать пользователю контроль над объёмом и форматом человекочитаемого CLI-вывода, сохранив пригодность утилиты для скриптов.

**Функции:**
- Выбор краткого, стандартного и подробного представления.
- Настройка видимых категорий, устройств и групп показателей через параметры CLI и пользовательский конфигурационный файл.
- Настройка порядка разделов, цвета, заголовков и единиц только в пределах поддерживаемых вариантов.
- Параметры командной строки имеют приоритет над конфигурационным файлом.
- Возможность явно отключить цвет и управляющие последовательности для перенаправления в файл или pipe.
- Машиночитаемый формат имеет отдельную версионируемую схему и не зависит от языка, цвета и настроек человекочитаемого представления.
- Ошибочная настройка не должна скрывать критическое состояние без явного выбора пользователя и не должна останавливать базовый вывод.

**Готово, когда:** один и тот же обработанный снимок можно вывести в кратком, стандартном и подробном виде; параметры CLI предсказуемо переопределяют конфигурацию, а стабильный машиночитаемый вывод остаётся пригодным для автоматизации.

## 4. Что отображается в OLHM 1.0

| Раздел | Определение оборудования | Основные показатели |
|---|---|---|
| CPU | Модель, производитель, ядра, потоки | Общая загрузка, загрузка потоков, частоты, температура и потребление в ваттах при наличии |
| RAM | Доступный системе объём | Использовано, доступно, %, swap |
| GPU | Модель, производитель, драйвер | Загрузка, VRAM, частоты, температура — при поддержке драйвера |
| Накопители | Физические диски, ёмкость, разделы | Заполненность файловых систем, чтение/запись при наличии |
| Материнская плата | Производитель, модель, BIOS/UEFI при наличии | Доступные температуры и обороты вентиляторов |
| Сеть | Сетевые интерфейсы | Скорость приёма и передачи |
| Система | Дистрибутив, архитектура, ядро, графическое окружение и сессия | Uptime и количество пакетов по подтверждённым источникам |

**Разница между обязательным и условным:** обнаружение перечисленных категорий является целью 1.0; конкретный датчик отображается только при реальной поддержке оборудованием, драйвером и доступными правами.

## 5. Источники данных в Linux

Основной подход — использовать стандартные интерфейсы ядра и официальные библиотеки драйверов. Не создавать собственные драйверы и не требовать root без необходимости.

- **CPU:** `/proc/cpuinfo`, `/proc/stat`, `/sys/devices/system/cpu/`, `cpufreq`, `hwmon`; для потребления — поддерживаемые CPU-package зоны RAPL в `/sys/class/powercap/` (`energy_uj`, `max_energy_range_uj`, при наличии `power_uw`). Мощность по энергии: Δмикроджоулей / 1 000 000 / Δсекунд по монотонным часам. При уменьшении счётчика интервал пропускается и берётся новая база; лимиты `constraint_*_power_limit_uw` не используются как измерение.
- **RAM:** `/proc/meminfo`.
- **GPU:** PCI/DRM/sysfs; для отдельных показателей — поддерживаемые интерфейсы соответствующих драйверов, в том числе AMDGPU и NVIDIA NVML при наличии.
- **Накопители:** `/sys/block/`, системные сведения о файловых системах и доступные счётчики I/O.
- **Материнская плата и датчики:** `/sys/class/dmi/id/`, `hwmon`, по возможности `libsensors` для корректных подписей и преобразований.
- **Сеть:** `/sys/class/net/` и системные счётчики трафика.
- **Система:** `/etc/os-release`, `uname` или эквивалентные интерфейсы libc, `/proc/uptime`, подтверждённые интерфейсы поддерживаемых менеджеров пакетов и переменные текущей графической сессии (`XDG_CURRENT_DESKTOP`, `XDG_SESSION_TYPE` и другие доступные признаки). Для версии окружения и имени композитора использовать отдельные проверяемые адаптеры; отсутствие данных не восполнять догадками.

Важные правила: CPU-загрузка и скорость передачи данных рассчитываются по **разности двух измерений**; `MemAvailable` не следует путать с `MemFree`; нельзя гарантировать температуру, мощность, частоты или загрузку GPU на любом оборудовании. Структура драйверов и доступность датчиков различаются.

Точный язык программирования, GUI-фреймворк и формат внутренней модели данных выбираются до реализации 0.1–0.4. Требование одно: **ядро мониторинга не зависит от графического интерфейса**.

## 6. Правила качества и проверки

1. **Достоверность.** Никаких придуманных температур, частот или нулей вместо отсутствующего датчика. Неизвестное значение так и помечается.
2. **Правильная идентификация.** Датчик нельзя подписывать как CPU/GPU, если его принадлежность не подтверждена.
3. **Минимальные права.** Основные функции должны работать от обычного пользователя; отсутствие доступа к отдельным сведениям — штатный случай.
4. **Низкая нагрузка.** Опрос не должен заметно нагружать систему; неудачное чтение не должно вызывать бесконечные повторные обращения.
5. **Отзывчивый GUI.** Опрос оборудования не блокирует перерисовку интерфейса.
6. **Проверяемость.** Результаты сверяются с системными инструментами Linux, при этом учитываются различия методик измерения и интервалов опроса.
7. **Совместимость.** Протестировать как минимум разные CPU Intel/AMD, разные варианты GPU/драйверов, системы без отдельных датчиков и несколько актуальных дистрибутивов Linux.
8. **Чистые границы слоёв.** Сборщики ничего не знают о внешнем виде интерфейса; GUI не читает `/proc` и `/sys` напрямую.
9. **Открытость.** Репозиторий содержит инструкцию сборки, правила участия и выбранную лицензию открытого ПО.

## 7. Порядок выполнения работ внутри каждой версии

1. Определить минимальный набор данных и условия их доступности.
2. Реализовать сбор данных.
3. Реализовать обработку, проверки и единицы измерения.
4. Подключить вывод: сначала CLI, затем существующий GUI.
5. Проверить на реальном оборудовании и зафиксировать ограничения.
6. Выпустить рабочую версию и только потом переходить к следующей.

**Правило проекта:** не начинать следующую категорию оборудования, пока текущая не имеет законченного рабочего результата.

## 8. Границы проекта на момент 1.0

OLHM 1.0 отвечает на три вопроса:

1. **Что установлено в компьютере?**
2. **Какие основные показатели этого оборудования доступны Linux?**
3. **Как эти показатели изменяются прямо сейчас?**

Всё, что связано с нагрузочным тестированием и расширенной диагностикой, остаётся **за пределами дорожной карты до 1.0**.

**Ближайшая задача:** реализовать **OLHM 0.1 — определение CPU в консоли**. Это первая точка, с которой начинается практическая разработка.
