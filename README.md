# OLHM — Open Linux Hardware Monitor

[English](README.en.md) | Русский

OLHM 0.7 — графический и консольный монитор CPU, RAM, накопителей и GPU с отдельными слоями Collection,
Processing и Presentation и общей моделью устройств и показателей. Доступны сведения о CPU,
общая и поточная загрузка, текущие частоты, температуры и критические пороги
поддерживаемых CPU-датчиков, троттлинг и потребление CPU-пакетов в ваттах.
Для памяти доступны системный объём RAM, использовано / доступно / всего,
процент использования и общий объём / использование swap.
Runtime использует Linux `/proc`, `/sys` и `statvfs`, без Nix-specific источников.
Для накопителей необязательно используются `lsblk` и `smartctl`: прямой запуск
с аргументами, без shell. `serde` и `serde_json` используются для JSON.
GPU используют Linux DRM/sysfs/hwmon, Intel PMU и необязательную NVML из драйвера NVIDIA.

## Графическое окно CPU, RAM, накопителей и GPU

```sh
nix-shell --run 'cargo run --features gui -- gui cpu'
nix-shell --run 'cargo run --features gui -- gui cpu --interval 0.5'
nix-shell --run 'cargo run --features gui -- gui ram'
nix-shell --run 'cargo run --features gui -- gui storage'
nix-shell --run 'cargo run --features gui -- gui gpu'
```

Окно показывает модель и характеристики CPU, общую загрузку, загрузку и частоту
каждого логического процессора, поддерживаемые температуры, критические пороги,
троттлинг за последний интервал и потребление CPU-пакетов.
При большом числе потоков или датчиков содержимое прокручивается. Отсутствующие
данные, ожидание второго замера, ошибки чтения и запрет доступа показаны явно.
В верхней части окна можно переключаться между CPU и RAM. Раздел RAM показывает
подписанные объёмы памяти, процент использования и swap. Переключение запускает
сессию выбранного модуля в фоновом потоке.

Обнаружение и опрос выполняются в отдельном потоке через `MonitorSession`; окно
получает только готовые снимки. Хранится один последний кадр без накопления истории.
При задержке опроса последний кадр помечается как устаревающий; при ошибке запуска
сессии можно повторить подключение. Закрытие окна прерывает ожидание очередного опроса.

GUI использует опциональный `egui/eframe` с OpenGL, поддержкой Wayland и X11 и
встроенными шрифтами. Нужны графическая сессия и системные библиотеки OpenGL,
libxkbcommon и соответствующего оконного протокола; `shell.nix` задаёт пути к ним
для NixOS. В сборке по умолчанию GUI выключен: используйте `--features gui`.
Без этого флага CLI собирается отдельно, а команда `gui` объясняет способ включения.
Запуск без аргументов по-прежнему выводит raw JSON.

## CPU в терминале

```sh
nix-shell --run 'cargo run -- help'
nix-shell --run 'cargo run -- info cpu'
nix-shell --run 'cargo run -- snapshot cpu --interval 1'
nix-shell --run 'cargo run -- monitor cpu'
nix-shell --run 'cargo run -- monitor cpu --interval 0.5 --count 5'
```

`info cpu` показывает производителя, модель, архитектуру и количество логических
процессоров и физических ядер, когда данных достаточно. `snapshot cpu` делает два
замера и печатает один готовый слепок без цикла и ANSI-кодов. `monitor cpu` обновляет
показатели до нажатия Ctrl+C. `--interval` задаёт интервал в секундах от 0.1 до 60
(по умолчанию 1, также для `snapshot`); `--count` в режиме `monitor` ограничивает число кадров, включая первый кадр с
ожиданием второго замера. В обычном терминале экран перерисовывается; при
перенаправлении stdout и при `TERM=dumb` кадры выводятся последовательно без ANSI-кодов.
Для текстовых команд закрытие принимающей стороны pipe завершает вывод без
сообщения об ошибке.

## Оперативная память и swap

```sh
nix-shell --run 'cargo run -- info ram'
nix-shell --run 'cargo run -- snapshot ram --interval 0.5'
nix-shell --run 'cargo run -- monitor ram --interval 1 --count 5'
```

Данные берутся из `/proc/meminfo`. Общий объём — `MemTotal`: RAM, доступная Linux,
а не паспортная ёмкость установленных модулей. Доступно — `MemAvailable`,
использовано — `MemTotal − MemAvailable`, процент — использовано / всего × 100.
`MemAvailable` учитывает возможность освобождения части кеша и не заменяется
`MemFree`. При его отсутствии использованный объём и процент помечаются недоступными.
Методика соответствует [описанию meminfo в документации Linux](https://docs.kernel.org/filesystems/proc.html#meminfo).

Для swap показываются `SwapTotal` и `SwapTotal − SwapFree`. Когда swap не настроен
и ядро сообщает нулевые счётчики, выводится `0 B`; отсутствие полей показывается
как недоступность. Значения `kB` в proc переводятся в байты с множителем 1024,
а интерфейс использует KiB / MiB / GiB / TiB. Ошибки единиц, переполнение и
несогласованные значения не подменяются нулями и не останавливают мониторинг.

RAM не требует второго замера для расчёта: первый кадр `monitor ram` уже содержит
показатели. `snapshot ram` сохраняет общий двухзамерный режим команды и печатает
один итоговый кадр. `info ram` показывает объём на момент запуска; мониторинг
перечитывает объём, доступную память и swap при каждом опросе. В контейнерах
показываются сведения доступного `/proc/meminfo`, а не отдельный лимит cgroup.
Доступные записи SMBIOS Type 17 дополняют раздел количеством установленных устройств
памяти, слотами, объёмом, производителем, моделью и настроенной скоростью при запуске.
Пустые слоты не считаются установленными модулями. Если чтение закрыто правами,
показывается «нет доступа»; утилита не запрашивает root.
Формат записей описан в [спецификации SMBIOS](https://www.dmtf.org/sites/default/files/standards/documents/DSP0134_3.8.0.pdf).

При наличии драйверов `ee1004` / `spd5118` читается опубликованный ядром SPD DDR4/DDR5.
Проверяется CRC базовых параметров; отображаются модель, серийный номер, код
производителя JEDEC, поддерживаемая геометрия, паспортные скорость и задержки
tAA/tRCD/tRP/tRAS. Неподдерживаемая геометрия не угадывается. SPD не сообщает
текущие тайминги контроллера и активный профиль XMP/EXPO. Настроенная скорость
SMBIOS, если доступна, показывается отдельно от паспортной скорости SPD;
MT/s и расчётная тактовая частота DDR в МГц подписаны раздельно.
Описания SMBIOS/SPD объединяются только при уникальном совпадении модели и
непустого серийного номера; иначе источники показаны отдельно и не суммируются.
Число видимых SPD-устройств может не охватывать всю память системы.

Температуры модулей читаются из подтверждённых датчиков `jc42` / `spd5118` и
обновляются при опросе. Привязка к SPD-модулю производится по одному устройству
sysfs, а не по порядку датчиков. Непривязанные датчики памяти показываются отдельно.
SMBIOS и SPD читаются один раз при открытии RAM-сессии.
Интерфейсы датчиков описаны в документации
[spd5118](https://docs.kernel.org/hwmon/spd5118.html) и
[jc42](https://docs.kernel.org/hwmon/jc42.html).

Помимо суммарного swap из meminfo, выводится каждый активный источник из
`/proc/swaps`: путь, тип, объём, занято и приоритет. zram выделяется отдельно от
swap-файла. Для zram показываются виртуальная ёмкость, объёмы несжатых и сжатых
данных, фактически выделенная RAM и алгоритм сжатия. Виртуальная ёмкость zram
не прибавляется к физической RAM; суммарный swap явно подписан как включающий
все источники. Чтение выполняется через стандартные интерфейсы без сканирования
SMBus, загрузки драйверов и изменения настроек памяти.
Значения zram соответствуют [документации ядра](https://docs.kernel.org/admin-guide/blockdev/zram.html).

## Накопители и файловые системы (0.6)

```sh
nix-shell --run 'cargo run -- info storage'
nix-shell --run 'cargo run -- snapshot storage --interval 1'
nix-shell --run 'cargo run -- monitor storage --interval 1 --count 5'
nix-shell --run 'cargo run --features gui -- gui storage'
```

Накопители, разделы и смонтированные файловые системы показаны раздельно.
Доступны модель, серийный номер, ёмкость, тип/транспорт, GPT/MBR, номера и
смещения разделов, тип ФС, метки, UUID и точки монтирования — когда источники
предоставляют эти сведения. Логические блочные устройства не выдаются за
физические диски; их зависимости перечислены отдельно. zram остаётся в RAM.

По `/sys/class/block/*/stat` рассчитываются текущие скорости чтения/записи
в байтах в секунду, по двум замерам с собственным интервалом устройства.
При первом замере, сбросе счётчиков или замене устройства нужен новый baseline.
Размер сектора этих счётчиков — всегда 512 байт, независимо от размера блока диска
([документация Linux](https://docs.kernel.org/admin-guide/iostats.html)).

Для ФС показаны размер, занято, доступно обычному пользователю, свободно с
резервом и заполненность `занято / (занято + доступно)`. Ёмкость определяется
через `statvfs` по точке монтирования, а не по размеру раздела. Диски, разделы,
bind-mount и Btrfs subvolumes не суммируются в общий объём. Видны монтирования
текущего mount namespace; сетевые и FUSE-монтирования перечисляются без вызова
потенциально зависающего запроса заполненности. Несмонтированная ФС может иметь
сигнатуру, но её свободное место не определяется.

Температуры обновляются через подтверждённые sysfs-привязки hwmon `nvme` /
`drivetemp`; запасной источник — SMART. Температура NVMe может относиться ко
всему контроллеру, а не отдельному namespace. Нет датчика — нет выдуманного нуля.

`lsblk` (util-linux) необязателен: дополняет модель и сведения о разметке/ФС.
`smartctl` (smartmontools с JSON) необязателен: читает состояние SMART, температуру,
NVMe critical warning, износ/резерв и доступные счётчики ошибок; для ATA — известные
атрибуты переназначенных, ожидающих и неисправимых секторов. SMART опрашивается
не чаще раза в 60 секунд; возраст результата подписан. Это только чтение:
самотесты, изменение параметров и запрос повышения прав не выполняются.
Для ATA используется проверка standby без пробуждения диска; поддержка USB/SAS
зависит от драйвера/моста и может быть недоступна. Отсутствие доступа, утилиты или
поддержки не означает исправность. PASSED — лишь собственная пороговая оценка
накопителя, не гарантия здоровья. Универсальный «процент здоровья SSD» не вычисляется.
Команды внешних адаптеров имеют ограничение времени и размера ответа.

## Видеокарты (0.7)

```sh
nix-shell --run 'cargo run -- info gpu'
nix-shell --run 'cargo run -- snapshot gpu --interval 1'
nix-shell --run 'cargo run -- monitor gpu --interval 1 --count 5'
nix-shell --run 'cargo run --features gui -- gui gpu'
```

Вкладка GPU и CLI показывают несколько видеокарт независимо. Обнаружение идёт
через PCI/DRM, идентичность включает аппаратный путь и sysfs inode; номера
`cardN`/`renderDN` не используются как идентификаторы видеокарт. Новые датчики
переобнаруживаются раз в 5 секунд, их принадлежность GPU перепроверяется при
опросе. Неизменные названия и привязки кешируются; GUI получает готовые данные
из фонового потока. Название берётся из NVML, product_name, базы udev или pci.ids.
Если PCI ID соответствует семейству моделей, название семейства сохраняется
без угадывания конкретной модификации. Версия NVIDIA-драйвера берётся из NVML,
остальных — из модуля/версии ядра с соответствующей подписью.

Доступные основные показатели:

- GPU Load, активность контроллера памяти и видеоблоков, когда драйвер их экспортирует.
- Основная температура, Hot Spot, Memory Junction и отдельные критические пороги.
- Текущие частоты GPU и памяти; Hz, MHz и активные DPM-частоты не смешиваются.
- Текущая и максимальная скорость PCIe, а также текущее и максимальное число линий.
- Объём, использование, свободная память и процент использования пула памяти.
- Мощность, Power Limit и процент его использования только для совпадающих
  областей измерения. Превышение 100% не обрезается и само по себе не означает троттлинг.
- Отдельные вентиляторы, RPM и доступный относительный уровень/PWM с точными подписями.
- Температурное/мощностное ограничение только по явным причинам драйвера.

Неподдерживаемые показатели явно подписаны, в GUI собраны в раскрываемый список.
Ошибки чтения и доступа не превращаются в нули. Остановка вентилятора может
давать настоящий `0 RPM`; процент PWM не выдаётся за измеренный процент RPM.

### NVIDIA

NVML загружается из `libnvidia-ml.so.1` динамически, без обязательной зависимости
сборки от NVIDIA SDK и без вызовов `nvidia-smi`. Устройство сопоставляется по PCI BDF.
Читаются GPU/memory utilization, framebuffer memory, мощность и Power Limit,
температура GPU, NVML memory temperature (при поддержке), текущие clocks,
Encode/Decode и доступные независимые вентиляторы. Новая API RPM используется
при наличии символа в драйвере; старые драйверы могут предоставлять только проценты.
Проценты NVML описывают заданную относительную скорость, а не гарантируют
фактическое вращение — для него нужен RPM.

GPU Hot Spot не подменяется основной температурой: у обычной NVML нет
универсального датчика Hot Spot для всех GeForce. Тип памяти подписан как
NVML framebuffer, не BAR и не вся системная RAM. Мощность включает GPU и
связанную схему; окно усреднения определяется драйвером (на многих Ampere+
около секунды). Thermal/Power Throttling используют current/supported event
reasons; общий HW Slowdown не интерпретируется как доказанная тепловая причина.
Отсутствие библиотеки или поддержки API оставляет GPU видимым через PCI/DRM.

### AMD

В Linux используются `amdgpu`/`radeon` sysfs и подтверждённые hwmon-каналы.
[ADLX поддерживает Windows](https://gpuopen.com/manuals/ADLX/adlx-page_guide_os/),
поэтому Windows DLL в Linux не вызываются.
Доступны gpu_busy_percent/mem_busy_percent, VRAM/GTT, частоты, температуры,
вентиляторы, мощность и power cap в пределах интерфейсов драйвера.

DRM AMDGPU_INFO_DEV_INFO определяет APU по FUSION-флагу. Его UMA-пул
подписывается как используемая RAM, а GTT — как отдельный бюджет/использование
разделяемой памяти. Эти значения не складываются с физической VRAM. При
недоступности DRM-запроса тип пула остаётся неподтверждённым, а не угадывается
по его размеру. Мощность hwmon PPT/SoC на APU может включать CPU; она не
называется потреблением только графического чипа или всей платы.

Для дополнительных метрик разбираются проверенные layout `gpu_metrics`:
1.1–1.3 — температуры, активность, частоты, совместная Video-активность;
1.3 — ASIC-independent причины троттлинга; 1.4–1.5 — базовые температуры,
активность и отдельные VCN-блоки (Encode/Decode совместно). Неизвестные версии
и поля-сентинелы не декодируются по догадке. ASIC-dependent throttle_status
не используется как универсальная битовая маска. Для других layout остаётся
доступен обычный sysfs/hwmon-набор, включая APU с `gpu_metrics` 2.x.

### Intel

Поддержаны Linux-драйверы i915 и xe: DRM-запросы регионов памяти, hwmon,
текущие GT-частоты и доступные причины ограничений. Разделяемая RAM iGPU
не выдаётся за физическую VRAM. Xe предоставляет оценки занятой локальной
и системной памяти. I915 без CAP_PERFMON/CAP_SYS_ADMIN может возвращать
фиктивное «всё свободно»; OLHM не интерпретирует такой ответ как достоверный
нулевой расход. Учёт использования system-memory у i915 не заявлен.

Device-wide загрузка отдельных движков читается через Intel PMU:
i915 — Δbusy_ns / Δenabled_ns, xe — Δactive_ticks / Δtotal_ticks.
Первый опрос, сброс, отсутствие прогресса и запрет perf_event различаются.
Отдельный render/copy/video engine не называется общей загрузкой всего GPU,
а общий процент не получается суммированием пересекающихся активностей.
Video engine Intel может обслуживать одновременно Encode/Decode — вывод
отражает совместную активность без выдуманного разделения.
Доступность PMU зависит от ядра и политики perf_event; права и sysctl не меняются.
При отсутствии разрешения остальные показатели продолжают работать.
[Intel IGCL](https://github.com/intel/drivers.gpu.control-library) ориентирован
на Windows-драйвер; Linux-сборка использует собственные интерфейсы i915/xe.

Чтение выполняется без записи в аппаратные интерфейсы, установки драйверов,
самотестов, разгона и изменения лимитов. Переносимая статическая musl-сборка
может не поддерживать динамическую загрузку NVML; для NVIDIA-телеметрии
нужна GUI/CLI-сборка с поддержкой динамических библиотек.

Первичные описания интерфейсов: [AMDGPU](https://docs.kernel.org/gpu/amdgpu/thermal.html),
[NVML](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html),
[Intel Xe frequencies](https://docs.kernel.org/gpu/xe/xe_gt_freq.html),
[Linux DRM UAPI](https://github.com/torvalds/linux/tree/master/include/uapi/drm).

## Источники показателей CPU

Загрузка рассчитывается по разности двух последовательных чтений `/proc/stat`.
Время idle и iowait не считается занятым, steal включается в занятое время;
guest и guest_nice не прибавляются повторно к user/nice. Общая загрузка берётся из
агрегированных счётчиков, а не из среднего округлённых процентов потоков.
Интервал измеряется монотонными часами. Первый замер, отсутствие изменения,
уменьшение счётчиков, отключённый CPU, отсутствие данных, ошибка чтения и отсутствие
доступа отображаются отдельными состояниями. После ошибки или сброса нужны новые
последовательные измерения; устаревшая загрузка не сохраняется.

Частоты читаются из per-CPU `cpufreq/scaling_cur_freq` и переводятся из кГц в МГц.
Это показатель, предоставленный драйвером, а не гарантированная аппаратная частота.
Без этого интерфейса частота показывается как недоступная.

CPU-температуры поддерживаются для hwmon-драйверов `coretemp` (Intel) и `k10temp`
(AMD/Hygon). Выводятся отдельные каналы с исходными подписями и именем устройства;
значения преобразуются из миллиградусов в °C. Tctl отдельно подписан как
управляющее значение. Каналы других драйверов не приписываются CPU, даже если
в их названии есть CPU. Отсутствие подходящего датчика — штатная ситуация.

Критический порог берётся из `temp*_crit` подтверждённых CPU-датчиков.
Критическая температурная тревога выводится отдельно: флаг `coretemp` может быть
сохранённым после прошлого перегрева. Тепловой троттлинг показывает новые события
или прирост учтённого времени за интервал по `core/package_throttle_count` и
`core/package_throttle_total_time_ms`. Это сведения счётчиков ядра, а не
гарантированное мгновенное состояние ограничения частоты. При отсутствии
поддерживаемого источника показывается «не поддерживается»; первый замер счётчика
ожидает сравнения.

Потребление берётся из поддерживаемых package-зон RAPL (`intel-rapl` и
`intel-rapl-mmio`). При наличии `power_uw` значение переводится из мкВт в Вт;
иначе средняя мощность за интервал рассчитывается как Δэнергии в мкДж / 1 000 000 /
Δсекунд по времени самих чтений энергии. Первый замер не содержит расчётной мощности.
Сброс или переполнение счётчика вызывает пропуск интервала и новый базовый замер.
Пакеты показаны раздельно, их поддомены не прибавляются повторно; лимиты мощности
и TDP не используются как измерения. Без доступа к счётчику выводится «нет доступа».

Описание счётчиков и датчиков:
[Linux /proc](https://docs.kernel.org/filesystems/proc.html),
[coretemp](https://docs.kernel.org/hwmon/coretemp.html),
[k10temp](https://docs.kernel.org/hwmon/k10temp.html),
[powercap](https://docs.kernel.org/power/powercap/powercap.html).

## Сбор и экспорт

```sh
nix-shell --run 'cargo run -- collect cpu --format json'
nix-shell --run 'cargo run -- collect cpu --format debug'
nix-build portable.nix
./result/bin/olhm collect cpu --format json > snapshot.json
```

Без аргументов программа также собирает CPU и выводит JSON. `help`, `--help` и `-h` показывают
доступные команды. Неверные аргументы завершают программу с ошибкой до collection.
JSON пишется в stdout, ошибки — в stderr; команды Nix могут дополнительно печатать
сообщения окружения, поэтому для чистого файла используйте собранный бинарник:
`./target/release/olhm collect cpu --format json > snapshot.json`.

JSON-документ содержит `schema_version: 1` и `snapshot` с полями raw-модели.
Timestamp сериализуется как `secs_since_epoch` и `nanos_since_epoch` (UTC Unix time).
Недоступные Option-поля представлены `null`, пустые доступные interfaces — пустыми
массивами/объектами. Ключи CPU в `proc_stat.cpus` — строки с десятичными CPU IDs.
Записи cpuinfo — массивы пар, сохраняющие порядок и повторяющиеся ключи.
Capabilities — карта путей в объекты вида `{"status":"not_available"}` либо
`{"status":"permission_denied","message":"..."}`; также предусмотрены
`available`, `read_error`, `parse_error`.

Строки, пробелы, переводы строк, kernel units и u64 counters сохраняются без
нормализации. JSON-потребителям следует использовать точные целочисленные типы:
JavaScript Number не представляет точно все u64. Несовместимые изменения формата
потребуют увеличения `schema_version`; дополнительные raw-атрибуты могут появляться
в зависимости от kernel. Debug-формат предназначен для ручной диагностики.
Экспорт остаётся инструментом диагностики Collection: формат raw JSON не меняется
при добавлении обработанных показателей мониторинга.

## Архитектура

- `collector`: общий trait `Collector` и чтение Linux interfaces.
- `collector/cpu`: parsers proc, обнаружение CPU и чтение sysfs, hwmon,
  thermal и powercap.
- `raw/cpu.rs`: исходные CPU данные, clock-tick counters, строковые атрибуты,
  timestamp начала чтения и карта доступности путей.
- `error.rs`: NotAvailable, PermissionDenied, ReadError, ParseError;
  fatal CollectError возникает только при отсутствии всех основных CPU источников.
- `raw/cpu_monitor.rs`: динамические чтения, статусы и монотонное время замера.
- `collector/cpu/monitor.rs`: опрос счётчиков, online CPU, частот и значений датчиков.
- `collector/memory`: чтение meminfo, SMBIOS/SPD, датчиков памяти и swap/zram.
- `raw/memory.rs`: исходные данные памяти и статусы доступности интерфейсов.
- `processing/memory.rs`: проверка RAM/swap, расчёты и перевод в общую модель.
- `processing/memory_details`: проверка SMBIOS/SPD, привязка температур и отдельные swap-источники.
- `collector/storage`: sysfs-топология, mountinfo/statvfs, hwmon и необязательные lsblk/smartctl.
- `raw/storage.rs`: исходные данные накопителей и локальные статусы ошибок.
- `processing/storage`: разметка, ёмкости ФС, дельты I/O и интерпретация SMART.
- `collector/gpu`: PCI/DRM-инвентаризация, кеш источников sysfs/hwmon, NVML и Intel PMU.
- `raw/gpu.rs`: исходные показания GPU с единицами, источниками и ошибками.
- `processing/gpu`: проверка значений, память/мощность, дельты PMU и versioned AMD metrics.
- `processing/cpu.rs`: обработанные статические сведения о CPU.
- `processing/cpu_monitor.rs`: расчёт загрузки/потребления, нормализация частот/температур,
  проверка значений и идентификация поддерживаемых CPU-датчиков.
- `model.rs`: общие `Device`, `Property`, `Metric`, `Unit`, `MetricValue`,
  `DeviceReading` и `MonitorSnapshot`, включая идентификаторы и связи устройств.
- `processing/cpu_model.rs`: перевод обработанных CPU-данных в общую модель.
- `monitor.rs`: интерфейс `MonitorSession`, CPU/RAM/storage/GPU-сессии и регистрация категорий.
  Сессия связывает Collection и Processing, не занимаясь выводом.
- `presentation/text.rs`: общий текстовый вывод; зависит только от `model` и std,
  не читает аппаратные интерфейсы и не содержит CPU-специфичных расчётов.
- `presentation/format.rs`: единые подписи единиц и состояний для CLI и GUI.
- `presentation/gui.rs`: окно CPU/RAM/накопителей/GPU; использует только общую модель и API сессии.
- `presentation/gui_worker.rs`: фоновый опрос и ограниченный одним кадром обмен с окном.
- Остальные collectors пока не реализованы.

CLI-команды `info`, `snapshot` и `monitor` используют один интерфейс сессии и общий
вывод. Для нового модуля потребуется реализация его сбора/обработки и регистрация
в `monitor.rs`; менять цикл CLI и текстовый renderer не требуется. Диагностическая
команда `collect cpu` сохраняет исходный raw JSON со `schema_version: 1`.

`CpuCollector::with_roots` позволяет тестировать чтение на временных fixture-деревьях.
Tests не зависят от hardware машины.

Тесты покрывают расчёт загрузки/потребления, guest-счётчики, сброс/переполнение,
ошибки и восстановление, CPU hotplug, единицы и состояния общей модели, привязку
датчиков, параметры CLI и общий текстовый вывод. Есть проверки полной сессии на
фикстурах Intel/AMD, стабильности ID при одинаковых подписях датчиков, задержки
повторных чтений и сохранения известных CPU при недоступности источников.
Добавлены проверки фонового опроса без блокировки окна, остановки при длинном
интервале, передачи ошибки обнаружения и отрисовки состояний в GUI.
CLI проверен на AMD Ryzen 7 9700X под NixOS; пользователь предоставил результаты
запуска CLI 0.3.0 на реальном Intel Core i5-6300HQ (`testresults/resultI5*.txt`).
В Intel-результатах загрузка, частоты и coretemp доступны, RAPL показывает «нет доступа».
GUI проверен на виртуальном X11-дисплее Xvfb с реальными данными Ryzen: обновление
показателей, прокрутка к датчикам и штатное закрытие окна. Поддержка Wayland включена
в сборку, но запуск на Wayland в этой проверке не выполнялся.

## Источники

- `/proc/cpuinfo`: исходный текст и записи с произвольными, повторяющимися полями.
- `/proc/stat`: исходный текст, aggregate/per-CPU counters в порядке kernel,
  включая будущие counters; остальные строки сохраняются без интерпретации.
- `/proc/meminfo`: системный объём, доступная RAM и счётчики swap; собирается RAM-сессией.
- `/sys/devices/system/cpu/{online,offline,present,possible}`: исходные строки
  и CPU IDs из списков/ranges.
- Динамически обнаруженные `cpuN`: прямые файловые атрибуты, `online`,
  `topology/*`, `cache/index*/*`, `cpufreq/*`, `cpuidle/*`, `cpuidle/state*/*`,
  optional `thermal_throttle/*`.
- `/sys/devices/system/cpu/vulnerabilities/*`: полные строковые значения.
- `/sys/class/hwmon/hwmon*/*`: доступные temperature, voltage, power, energy,
  alarm и дополнительные каналы всех hwmon-устройств.
- `/sys/class/thermal/thermal_zone*/*`: температуры и trip points;
  `/sys/class/thermal/cooling_device*/*`: raw cooling/throttling states.
- `/sys/class/powercap/*/*`: energy counters, power limits и прочие атрибуты
  доступных powercap domains.

Sysfs атрибуты сохраняются с исходными пробелами и единицами: kHz остаётся
kHz, hwmon temperature обычно остаётся millidegree Celsius, voltage — millivolt,
power — microwatt, powercap energy — microjoule, cache size — строкой вроде `32K`.
Точные единицы определяет соответствующий Linux sysfs ABI. Неизвестные регулярные файлы
в перечисленных директориях читаются наравне с известными. Недоступные значения
не заполняются догадками. Отсутствие per-CPU `online` не означает `true`;
для таких CPU доступен отдельный глобальный online list.

## Ограничения

Сбор не атомарен: CPU hotplug и counters могут измениться между чтениями.
Ошибки отдельных файлов не прерывают сбор; проверяйте capabilities и Option.
Статус Available означает успешное чтение/перечисление, а не поддержку всех
возможных атрибутов. Ошибки дочерних файлов отражены отдельно.

Sysfs читается только на заданной глубине: обход произвольных symlink-деревьев,
vendor-specific пути, глобальные `cpufreq/policy*` и вложенные driver extensions
не реализованы. Per-CPU cpufreq-directory symlink и стандартные class symlinks
поддерживаются. Имена `hwmonN` нестабильны между загрузками, поэтому сохраняются
также атрибут `name` (если kernel его предоставляет) и canonical path устройства.
Raw Collection не определяет, какой hwmon/thermal/powercap канал относится именно к CPU:
стандартный class содержит также датчики платы, NVMe и других устройств. Эта
ассоциация и интерпретация alarm/cooling/throttle значений относится к Processing.
Текстовые интерфейсы должны содержать UTF-8; binary/non-UTF-8 файлы получают ReadError.
CPU list expansion ограничено 1 048 576 элементами; при превышении исходная
строка сохраняется с ParseError. При ошибке parsing proc результат соответствующего
parser отсутствует, диагностика остаётся в capabilities.

Монитор читает статическую информацию и обнаруживает датчики один раз при старте,
затем опрашивает только динамические данные. CPU hotplug учитывается в каждом
опросе; общая загрузка при изменении набора CPU требует нового базового замера.
Идентичность и подписи датчиков закреплены за обнаруженными canonical paths.
Пропавший канал становится недоступным, а восстановленный по тому же пути читается
снова. Для обнаружения новых датчиков или смены их пути нужно перезапустить монитор.
Статические сведения в шапке также обновляются при перезапуске.

Неудачные чтения файлов и каталога CPU повторяются не чаще раза в секунду;
успешные динамические значения не кешируются. После восстановления доступа
значение появится при следующей разрешённой попытке, а расчёту загрузки/мощности
понадобятся два корректных последовательных замера. Повреждённые значения не
подменяются последними успешными. Ошибки отдельных файлов не останавливают сессию.
CPU-список сохраняется при временной ошибке обнаружения. Доступные неизменные
метаданные не читаются на каждом такте; недоступные метаданные диапазона энергии
перепроверяются с той же паузой. На каждом такте опрашиваются только выбранные
Processing CPU-датчики и package-зоны. Монитор не сохраняет полную копию текста
`/proc/stat` и списков прерываний; raw-экспорт сохраняет их, как раньше.

Переносимая статическая CLI-сборка 0.6.0 для Linux x86_64 находится в
`dist/olhm-0.6.0-linux-x86_64.tar.gz`. Она предназначена для проверки CPU, RAM,
swap, накопителей и файловых систем на Debian/Ubuntu, Fedora, openSUSE, Arch,
Alpine и других x86_64 Linux без установки Rust или Nix. Контрольная сумма
находится в `dist/SHA256SUMS`, инструкция — внутри архива. GUI в переносимый
musl-пакет не входит; `portable.nix` собирает именно независимую CLI-версию.
Отдельный GUI-пакет `dist/olhm-0.7.0-gui-linux-x86_64.tar.gz` содержит launcher,
glibc и пользовательские X11/Wayland-библиотеки; OpenGL/EGL и видеодрайвер
используются из гостевой системы. Инструкция проверки находится внутри архива.
