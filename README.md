# OLHM — Open Linux Hardware Monitor

OLHM 0.4 — графический и консольный монитор CPU с отдельными слоями Collection,
Processing и Presentation и общей моделью устройств и показателей. Доступны сведения о CPU,
общая и поточная загрузка, текущие частоты, температуры поддерживаемых CPU-датчиков
и потребление CPU-пакетов в ваттах.
Runtime использует Linux `/proc` и `/sys`, без shell-команд
и без Nix-specific источников. `serde` и `serde_json` используются для экспорта raw snapshot.

## Графическое окно CPU

```sh
nix-shell --run 'cargo run --features gui -- gui cpu'
nix-shell --run 'cargo run --features gui -- gui cpu --interval 0.5'
```

Окно показывает модель и характеристики CPU, общую загрузку, загрузку и частоту
каждого логического процессора, поддерживаемые температуры и потребление CPU-пакетов.
При большом числе потоков или датчиков содержимое прокручивается. Отсутствующие
данные, ожидание второго замера, ошибки чтения и запрет доступа показаны явно.

Обнаружение и опрос выполняются в отдельном потоке через `MonitorSession`; окно
получает только готовые снимки. Хранится один последний кадр без накопления истории.
При задержке опроса последний кадр помечается как устаревающий; при ошибке запуска
сессии можно повторить подключение. Закрытие окна прерывает ожидание очередного опроса.

GUI использует опциональный `egui/eframe` с OpenGL, поддержкой Wayland и X11 и
встроенными шрифтами. Нужны графическая сессия и системные библиотеки OpenGL,
libxkbcommon и соответствующего оконного протокола; `shell.nix` задаёт пути к ним
для NixOS. В сборке по умолчанию GUI выключен: используйте `--features gui`.
Без этого флага CLI собирается отдельно, а команда `gui` объясняет способ включения.
Запуск без аргументов по-прежнему выводит raw JSON.

## CPU в терминале

```sh
nix-shell --run 'cargo run -- help'
nix-shell --run 'cargo run -- info cpu'
nix-shell --run 'cargo run -- snapshot cpu --interval 1'
nix-shell --run 'cargo run -- monitor cpu'
nix-shell --run 'cargo run -- monitor cpu --interval 0.5 --count 5'
```

`info cpu` показывает производителя, модель, архитектуру и количество логических
процессоров и физических ядер, когда данных достаточно. `snapshot cpu` делает два
замера и печатает один готовый слепок без цикла и ANSI-кодов. `monitor cpu` обновляет
показатели до нажатия Ctrl+C. `--interval` задаёт интервал в секундах от 0.1 до 60
(по умолчанию 1, также для `snapshot`); `--count` в режиме `monitor` ограничивает число кадров, включая первый кадр с
ожиданием второго замера. В обычном терминале экран перерисовывается; при
перенаправлении stdout и при `TERM=dumb` кадры выводятся последовательно без ANSI-кодов.
Закрытие принимающей стороны pipe завершает вывод без сообщения об ошибке.

Загрузка рассчитывается по разности двух последовательных чтений `/proc/stat`.
Время idle и iowait не считается занятым, steal включается в занятое время;
guest и guest_nice не прибавляются повторно к user/nice. Общая загрузка берётся из
агрегированных счётчиков, а не из среднего округлённых процентов потоков.
Интервал измеряется монотонными часами. Первый замер, отсутствие изменения,
уменьшение счётчиков, отключённый CPU, отсутствие данных, ошибка чтения и отсутствие
доступа отображаются отдельными состояниями. После ошибки или сброса нужны новые
последовательные измерения; устаревшая загрузка не сохраняется.

Частоты читаются из per-CPU `cpufreq/scaling_cur_freq` и переводятся из кГц в МГц.
Это показатель, предоставленный драйвером, а не гарантированная аппаратная частота.
Без этого интерфейса частота показывается как недоступная.

CPU-температуры поддерживаются для hwmon-драйверов `coretemp` (Intel) и `k10temp`
(AMD/Hygon). Выводятся отдельные каналы с исходными подписями и именем устройства;
значения преобразуются из миллиградусов в °C. Tctl отдельно подписан как
управляющее значение. Каналы других драйверов не приписываются CPU, даже если
в их названии есть CPU. Отсутствие подходящего датчика — штатная ситуация.

Потребление берётся из поддерживаемых package-зон RAPL (`intel-rapl` и
`intel-rapl-mmio`). При наличии `power_uw` значение переводится из мкВт в Вт;
иначе средняя мощность за интервал рассчитывается как Δэнергии в мкДж / 1 000 000 /
Δсекунд по времени самих чтений энергии. Первый замер не содержит расчётной мощности.
Сброс или переполнение счётчика вызывает пропуск интервала и новый базовый замер.
Пакеты показаны раздельно, их поддомены не прибавляются повторно; лимиты мощности
и TDP не используются как измерения. Без доступа к счётчику выводится «нет доступа».

Описание счётчиков и датчиков:
[Linux /proc](https://docs.kernel.org/filesystems/proc.html),
[coretemp](https://docs.kernel.org/hwmon/coretemp.html),
[k10temp](https://docs.kernel.org/hwmon/k10temp.html),
[powercap](https://docs.kernel.org/power/powercap/powercap.html).

## Сбор и экспорт

```sh
nix-shell --run 'cargo run -- collect cpu --format json'
nix-shell --run 'cargo run -- collect cpu --format debug'
nix-build portable.nix
./result/bin/olhm collect cpu --format json > snapshot.json
```

Без аргументов программа также собирает CPU и выводит JSON. `help`, `--help` и `-h` показывают
доступные команды. Неверные аргументы завершают программу с ошибкой до collection.
JSON пишется в stdout, ошибки — в stderr; команды Nix могут дополнительно печатать
сообщения окружения, поэтому для чистого файла используйте собранный бинарник:
`./target/release/olhm collect cpu --format json > snapshot.json`.

JSON-документ содержит `schema_version: 1` и `snapshot` с полями raw-модели.
Timestamp сериализуется как `secs_since_epoch` и `nanos_since_epoch` (UTC Unix time).
Недоступные Option-поля представлены `null`, пустые доступные interfaces — пустыми
массивами/объектами. Ключи CPU в `proc_stat.cpus` — строки с десятичными CPU IDs.
Записи cpuinfo — массивы пар, сохраняющие порядок и повторяющиеся ключи.
Capabilities — карта путей в объекты вида `{"status":"not_available"}` либо
`{"status":"permission_denied","message":"..."}`; также предусмотрены
`available`, `read_error`, `parse_error`.

Строки, пробелы, переводы строк, kernel units и u64 counters сохраняются без
нормализации. JSON-потребителям следует использовать точные целочисленные типы:
JavaScript Number не представляет точно все u64. Несовместимые изменения формата
потребуют увеличения `schema_version`; дополнительные raw-атрибуты могут появляться
в зависимости от kernel. Debug-формат предназначен для ручной диагностики.
Экспорт остаётся инструментом диагностики Collection: формат raw JSON не меняется
при добавлении обработанных показателей мониторинга.

## Архитектура

- `collector`: общий trait `Collector` и чтение Linux interfaces.
- `collector/cpu`: parsers proc, обнаружение CPU и чтение sysfs, hwmon,
  thermal и powercap.
- `raw/cpu.rs`: исходные CPU данные, clock-tick counters, строковые атрибуты,
  timestamp начала чтения и карта доступности путей.
- `error.rs`: NotAvailable, PermissionDenied, ReadError, ParseError;
  fatal CollectError возникает только при отсутствии всех основных CPU источников.
- `raw/cpu_monitor.rs`: динамические чтения, статусы и монотонное время замера.
- `collector/cpu/monitor.rs`: опрос счётчиков, online CPU, частот и значений датчиков.
- `processing/cpu.rs`: обработанные статические сведения о CPU.
- `processing/cpu_monitor.rs`: расчёт загрузки/потребления, нормализация частот/температур,
  проверка значений и идентификация поддерживаемых CPU-датчиков.
- `model.rs`: общие `Device`, `Property`, `Metric`, `Unit`, `MetricValue`,
  `DeviceReading` и `MonitorSnapshot`, включая идентификаторы и связи устройств.
- `processing/cpu_model.rs`: перевод обработанных CPU-данных в общую модель.
- `monitor.rs`: интерфейс `MonitorSession`, CPU-реализация и регистрация категорий.
  Сессия связывает Collection и Processing, не занимаясь выводом.
- `presentation/text.rs`: общий текстовый вывод; зависит только от `model` и std,
  не читает аппаратные интерфейсы и не содержит CPU-специфичных расчётов.
- `presentation/format.rs`: единые подписи единиц и состояний для CLI и GUI.
- `presentation/gui.rs`: окно CPU; использует только общую модель и API сессии.
- `presentation/gui_worker.rs`: фоновый опрос и ограниченный одним кадром обмен с окном.
- Остальные collectors пока не реализованы.

CLI-команды `info`, `snapshot` и `monitor` используют один интерфейс сессии и общий
вывод. Для нового модуля потребуется реализация его сбора/обработки и регистрация
в `monitor.rs`; менять цикл CLI и текстовый renderer не требуется. Диагностическая
команда `collect cpu` сохраняет исходный raw JSON со `schema_version: 1`.

`CpuCollector::with_roots` позволяет тестировать чтение на временных fixture-деревьях.
Tests не зависят от hardware машины.

Тесты покрывают расчёт загрузки/потребления, guest-счётчики, сброс/переполнение,
ошибки и восстановление, CPU hotplug, единицы и состояния общей модели, привязку
датчиков, параметры CLI и общий текстовый вывод. Есть проверки полной сессии на
фикстурах Intel/AMD, стабильности ID при одинаковых подписях датчиков, задержки
повторных чтений и сохранения известных CPU при недоступности источников.
Добавлены проверки фонового опроса без блокировки окна, остановки при длинном
интервале, передачи ошибки обнаружения и отрисовки состояний в GUI.
CLI проверен на AMD Ryzen 7 9700X под NixOS; пользователь предоставил результаты
запуска CLI 0.3.0 на реальном Intel Core i5-6300HQ (`testresults/resultI5*.txt`).
В Intel-результатах загрузка, частоты и coretemp доступны, RAPL показывает «нет доступа».
GUI проверен на виртуальном X11-дисплее Xvfb с реальными данными Ryzen: обновление
показателей, прокрутка к датчикам и штатное закрытие окна. Поддержка Wayland включена
в сборку, но запуск на Wayland в этой проверке не выполнялся.
Проверка GUI на другом физическом оборудовании и других дистрибутивах ещё требуется.

## Источники

- `/proc/cpuinfo`: исходный текст и записи с произвольными, повторяющимися полями.
- `/proc/stat`: исходный текст, aggregate/per-CPU counters в порядке kernel,
  включая будущие counters; остальные строки сохраняются без интерпретации.
- `/sys/devices/system/cpu/{online,offline,present,possible}`: исходные строки
  и CPU IDs из списков/ranges.
- Динамически обнаруженные `cpuN`: прямые файловые атрибуты, `online`,
  `topology/*`, `cache/index*/*`, `cpufreq/*`, `cpuidle/*`, `cpuidle/state*/*`,
  optional `thermal_throttle/*`.
- `/sys/devices/system/cpu/vulnerabilities/*`: полные строковые значения.
- `/sys/class/hwmon/hwmon*/*`: доступные temperature, voltage, power, energy,
  alarm и дополнительные каналы всех hwmon-устройств.
- `/sys/class/thermal/thermal_zone*/*`: температуры и trip points;
  `/sys/class/thermal/cooling_device*/*`: raw cooling/throttling states.
- `/sys/class/powercap/*/*`: energy counters, power limits и прочие атрибуты
  доступных powercap domains.

Sysfs атрибуты сохраняются с исходными пробелами и единицами: kHz остаётся
kHz, hwmon temperature обычно остаётся millidegree Celsius, voltage — millivolt,
power — microwatt, powercap energy — microjoule, cache size — строкой вроде `32K`.
Точные единицы определяет соответствующий Linux sysfs ABI. Неизвестные регулярные файлы
в перечисленных директориях читаются наравне с известными. Недоступные значения
не заполняются догадками. Отсутствие per-CPU `online` не означает `true`;
для таких CPU доступен отдельный глобальный online list.

## Ограничения

Сбор не атомарен: CPU hotplug и counters могут измениться между чтениями.
Ошибки отдельных файлов не прерывают сбор; проверяйте capabilities и Option.
Статус Available означает успешное чтение/перечисление, а не поддержку всех
возможных атрибутов. Ошибки дочерних файлов отражены отдельно.

Sysfs читается только на заданной глубине: обход произвольных symlink-деревьев,
vendor-specific пути, глобальные `cpufreq/policy*` и вложенные driver extensions
не реализованы. Per-CPU cpufreq-directory symlink и стандартные class symlinks
поддерживаются. Имена `hwmonN` нестабильны между загрузками, поэтому сохраняются
также атрибут `name` (если kernel его предоставляет) и canonical path устройства.
Raw Collection не определяет, какой hwmon/thermal/powercap канал относится именно к CPU:
стандартный class содержит также датчики платы, NVMe и других устройств. Эта
ассоциация и интерпретация alarm/cooling/throttle значений относится к Processing.
Текстовые интерфейсы должны содержать UTF-8; binary/non-UTF-8 файлы получают ReadError.
CPU list expansion ограничено 1 048 576 элементами; при превышении исходная
строка сохраняется с ParseError. При ошибке parsing proc результат соответствующего
parser отсутствует, диагностика остаётся в capabilities.

Монитор читает статическую информацию и обнаруживает датчики один раз при старте,
затем опрашивает только динамические данные. CPU hotplug учитывается в каждом
опросе; общая загрузка при изменении набора CPU требует нового базового замера.
Идентичность и подписи датчиков закреплены за обнаруженными canonical paths.
Пропавший канал становится недоступным, а восстановленный по тому же пути читается
снова. Для обнаружения новых датчиков или смены их пути нужно перезапустить монитор.
Статические сведения в шапке также обновляются при перезапуске.

Неудачные чтения файлов и каталога CPU повторяются не чаще раза в секунду;
успешные динамические значения не кешируются. После восстановления доступа
значение появится при следующей разрешённой попытке, а расчёту загрузки/мощности
понадобятся два корректных последовательных замера. Повреждённые значения не
подменяются последними успешными. Ошибки отдельных файлов не останавливают сессию.
CPU-список сохраняется при временной ошибке обнаружения. Доступные неизменные
метаданные не читаются на каждом такте; недоступные метаданные диапазона энергии
перепроверяются с той же паузой. На каждом такте опрашиваются только выбранные
Processing CPU-датчики и package-зоны. Монитор не сохраняет полную копию текста
`/proc/stat` и списков прерываний; raw-экспорт сохраняет их, как раньше.

Другие категории оборудования пока не реализованы. Переносимая статическая
CLI-сборка 0.3.0 для Linux x86_64 находится в `dist/olhm-0.3.0-linux-x86_64.tar.gz`;
она не содержит GUI 0.4. Текущая версия собирается из исходников. `portable.nix`
по-прежнему предназначен для отдельной статической CLI-сборки без GUI.
